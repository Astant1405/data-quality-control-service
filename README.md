# DQC Service (Модуль ККД)

Сервис для контроля качества данных (ККД) по целям и ключевым результатам (КР) сотрудников.
Реализован в рамках тестового задания.


## Быстрый старт (Docker Compose)


Проект полностью упакован в Docker и поднимается одной командой.
Перед запуском скопируйте шаблон переменных окружения:

cp .env.example .env

docker compose up --build


## После запуска сервис будет доступен по адресу: 

http://localhost:8080.


## Автоматическая инициализация
При первом запуске (когда база пуста) класс DataInitializer автоматически создает два прогона (RUN-001 и RUN-002), чтобы вы могли сразу проверить работу метрик и дельты.

Пример запроса для проверки сводки (дельта за 2-й прогон):

curl -i "http://localhost:8080/api/kkd/summary?run_id=2&unit_id=1"

(Где run_id=2 — это RUN-002, а unit_id=1 — Центральный аппарат).


## API Эндпоинты


- Список прогонов:
GET /api/runs

- Сводка метрик (с дельтой):
GET /api/kkd/summary?run_id={id}&unit_id={id}

- Список найденных проблем (с фильтрами и пагинацией):
GET /api/kkd/issues?run_id={id}&unit_id={id}&rule_code={code}&severity={level}&limit=20&offset=0

- Запуск нового прогона:
POST /api/runs (Body: {"runCode": "RUN-003", "snapshotDate": "2026-11-10", "comparedToRunCode": "RUN-002"})


Формат ошибок единый (как требуется в ТЗ): {"error": {"code": "...", "message": "..."}}. Неизвестные ID возвращают 404, невалидные параметры — 422.


## Тесты

Проект покрыт юнит-тестами (JUnit 5), которые не требуют поднятия HTTP-сервера или базы данных.
Покрыты сценарии: расчет метрик, расчет дельты и два правила на граничных данных (GOAL_NO_OWNER и KR_WEIGHTS_SUM).


Запуск тестов:

./mvnw clean test


## Миграции (Liquibase)

Схема БД и стартовые данные управляются через Liquibase. Скрипты лежат в src/main/resources/db/changelog/.
При запуске приложения миграции применяются автоматически.

Проверка наката и отката (требование ТЗ):

Накат (миграции накатываются при старте приложения): docker compose up -d

Приложение накатывает все таблицы и заполняет их стартовыми данными.


Откат (полная очистка базы данных): docker compose down -v

Флаг -v удаляет volume с данными PostgreSQL, возвращая базу в исходное (пустое) состояние. Если открыть pgAdmin, таблиц не будет.


Повторный накат: docker compose up --build -d

Приложение запускается с нуля, Liquibase снова создает таблицы и заливает данные. DataInitializer генерирует прогоны.


## Архитектура решения

Проект построен по слоистой архитектуре с выделением доменной логики:

- api — REST-контроллеры и DTO (ответы/запросы).

- engine — Движок правил ККД. Логика правил полностью изолирована от БД и API. Каждое правило реализует интерфейс KkdRule. KkdRuleEngine собирает их в цепочку и возвращает список найденных проблем.

- service — Оркестрация. KkdRunService запускает прогон (загружает контекст, прогоняет правила, считает метрики и сохраняет результаты). KkdSummaryService собирает ответ для API, рассчитывая дельту.

- repository — Spring Data JPA. Для сложных запросов (например, фильтрация по дереву подразделений или пагинация) используются нативные SQL-запросы с WITH RECURSIVE для максимальной производительности.

- model — JPA-сущности базы данных.


# Как считаются метрики:

- Загружаются все активные цели и КР в KkdContext.

- Движок правил находит проблемы (DetectedIssue).

- KkdMetricCalculator собирает статистику по каждому подразделению (с учетом дочерних подразделений).

- Результаты сохраняются в kkd_metric_snapshot и kkd_issue.


## Как считается дельта:

Сравниваются проблемы текущего и предыдущего прогонов. Проблема считается «той же самой», если совпадают код правила, тип объекта и ID объекта. На основе этого считаются newIssues, persistingIssues, resolvedIssues.
